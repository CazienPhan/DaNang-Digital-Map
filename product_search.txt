1. FEATURE OVERVIEW
================================================================================

WHAT IS PRODUCT SEARCH?
------------------------
Product Search is a search mode inside the SearchBar component that allows
users to search for local products (e.g. OCOP goods, regional specialties)
indexed in a Meilisearch instance. It operates entirely independently from the
existing Place (Destination) Search.

The user activates Product Search by clicking the "Product Search" tab in the
SearchModeSwitcher toggle beneath the search input. From that moment forward
every keystroke and every Enter-key action is routed to the Product Search
pipeline — never to Map4D.

WHAT PROBLEM DOES IT SOLVE?
-----------------------------
Da Nang's digital map platform serves both navigation users (looking for places
on the map) and consumers (looking for local products). Without Product Search,
a user who types "OCOP honey" would receive map POI results, not product
catalogue results. Product Search solves the discovery problem for commerce
data that has no geographic pin on the map.

DESTINATION SEARCH vs. PRODUCT SEARCH
---------------------------------------

  Destination Search (mode = "place")
  ------------------------------------
  Provider     : Map4D API (third-party mapping service)
  Backend path : GET /api/map4d/autosuggest (backend proxy to Map4D API)
  Index        : Map4D's own geographic POI database
  Results      : Places with latitude/longitude — clicking moves the map
  Icon         : MapPin (lucide-react)
  Location bias: YES — biased toward the user's current map center
  Engine class : Map4DSearchEngine

  Product Search (mode = "product")
  ----------------------------------
  Provider     : Meilisearch (self-hosted search engine)
  Backend path : GET /api/products/autocomplete and GET /api/products/search
  Index        : "products" Meilisearch index (product_types from Supabase)
  Results      : Product catalogue items with name, description, optional image
  Icon         : ShoppingBag (lucide-react)
  Location bias: NO — products are not geo-tagged; locationBias is ignored
  Engine class : ProductSearchEngine

WHY TWO DIFFERENT SEARCH PROVIDERS?
-------------------------------------
Map4D is the authoritative geographic data source for Da Nang. It has rich
POI, road, and address data — but it knows nothing about local product
catalogues. Meilisearch is a self-hosted, open-source search engine that
the team controls directly. It holds the product_types table, supports
Vietnamese typo-tolerance, Vietnamese stop-words, bilingual synonyms (café /
cà phê / coffee), and the custom OCOP dictionary entry.

Mixing both providers into a single endpoint would violate the Single
Responsibility Principle and would make future product features (filtering,
facets, category browsing) impossible to add cleanly. By separating them into
two independent engines behind one unified interface (SearchEngine), the
frontend SearchBar never needs to know which backend it is talking to.

LAYER EXPLANATIONS
-------------------

Layer 1 — User Input
  The user's keyboard events in the browser.

Layer 2 — SearchBar
  Top-level orchestrator. Owns all state: query string, searchMode,
  suggestions[], listingResults[], listingLoading, searchView.
  Never touches any search provider directly.

Layer 3 — SearchEngineAdapter
  The Strategy Pattern gateway. Built once per searchMode via useMemo.
  Exposes two methods: autocomplete() and search(). Both always return
  SearchSuggestion[]. Selects ProductSearchEngine when mode = 'product'.

Layer 4 — ProductSearchEngine
  Implements the SearchEngine interface. Calls ProductSearchService and
  passes results through SearchSuggestionMapper. The only class that
  knows about both ProductSearchService and SearchSuggestionMapper.

Layer 5 — ProductSearchService (frontend)
  A plain TypeScript static class. No React. No state. Performs HTTP
  fetch() calls to the backend. Unwraps the { success, data } envelope.
  Reads VITE_BACKEND_URL from environment.

Layer 6 — Backend HTTP Boundary
  Express server at port 5000. Routes mounted at /api/products.

Layer 7 — Controllers
  ProductSearchController: validates query, limit, offset; calls backend
  ProductSearchService; returns { success, data } envelope.
  ProductAutocompleteController: validates query, limit; calls
  productSearchService.autocomplete(); returns { success, data } envelope.

Layer 8 — Backend ProductSearchService
  Anti-corruption boundary. Queries Meilisearch via meiliClientPromise.
  Maps raw ProductSearchDocument hits to typed ProductListingItem[] or
  AutocompleteItem[]. Raw Meilisearch documents never escape this class.

Layer 9 — Meilisearch Client
  Singleton promise. Loads the meilisearch ESM package via dynamic import
  from CommonJS. Reads MEILISEARCH_HOST and MEILISEARCH_ADMIN_KEY from env.

Layer 10 — Meilisearch Index ("products")
  Contains ProductSearchDocument records. Settings applied via
  products.settings.ts: searchable attributes, filterable attributes,
  ranking rules, synonyms, typo tolerance, stop words, custom dictionary.

Layer 11 — SearchSuggestionMapper (frontend)
  Pure static class. The ONLY place where provider types are converted to
  SearchSuggestion. No side effects. No React.

Layer 12 — SearchSuggestion (frozen DTO)
  The ONLY type consumed by any UI component in the search feature.

Layer 13 — SearchResult (dropdown)
  Renders while user is typing. Fires onSelectSuggestion on click.

Layer 14 — SearchListing + SearchListingCard
  Renders after Enter key press. Shows loading spinner, empty state, and
  each product as a card with thumbnail + title + description.

3. COMPLETE USER FLOW
================================================================================

Step 1 — User opens the application.
  The SearchBar renders in 'idle' view. The SearchModeSwitcher shows
  "Place Search" as the active tab (default searchMode = 'place').

  ↓

Step 2 — User clicks "Product Search" tab.
  SearchModeSwitcher calls onChange('product').
  SearchBar.setSearchMode('product') fires.
  The useEffect([searchMode]) clears all stale suggestions, listingResults,
  listingQuery. If view was 'listing' or 'refining', it resets to 'idle'.
  useMemo([searchMode]) creates a new SearchEngineAdapter('product')
  which internally creates a ProductSearchEngine instance.

  ↓

Step 3 — User types a keyword (e.g. "mật ong").
  handleQueryChange fires on every keystroke.
  setQuery updates the controlled input value.
  The debouncedQuery (useDebounce, 350 ms) waits for the user to pause.
  While debouncedQuery.trim().length < 1, suggestions stay empty.

  ↓

Step 4 — Debounce fires (350 ms after last keystroke).
  The autocomplete useEffect triggers.
  searchView transitions to 'autocomplete' (if not already in listing).
  A new AbortController is created. The previous controller (if any)
  is aborted first via the cleanup function of the previous useEffect run.
  adapter.autocomplete(debouncedQuery, locationBias, signal) is called.
  → SearchEngineAdapter.autocomplete() delegates to ProductSearchEngine.autocomplete().
  → ProductSearchEngine calls ProductSearchService.autocomplete(query, signal).
  → ProductSearchService fetches:
      GET /api/products/autocomplete?query=m%E1%BA%ADt+ong
  → Backend: ProductAutocompleteController receives the request.
  → Backend validates query (non-empty), reads limit (default 5).
  → Backend ProductSearchService queries Meilisearch index "products"
    with attributesToRetrieve: ["name"], limit 5.
  → Meilisearch returns up to 5 hits with { name } only.
  → Backend maps hits to AutocompleteItem[] and wraps in AutocompleteResponse.
  → HTTP response: { success: true, data: { query, processingTimeMs,
    estimatedTotalHits, items: [{ name: "Mật ong rừng Sơn Trà" }, ...] } }
  → Frontend productSearch.service.ts extracts envelope.data.items.
  → ProductSearchEngine passes items[] to SearchSuggestionMapper.fromAutocompleteItems().
  → Mapper converts each { name } to SearchSuggestion:
      { id: name, type: 'product', title: name, description: '', original: item }
  → SearchBar.setSuggestions(results) fires.

  ↓

Step 5 — Dropdown (SearchResult) appears.
  SearchBar renders <SearchResult suggestions={suggestions} />.
  Each suggestion shows a ShoppingBag icon (type = 'product') + title.
  No description text (autocomplete items carry name only).

  ↓

Step 6a — User selects a dropdown item.
  handleSuggestionSelect(suggestion) fires.
  suggestion.type === 'product' → the code logs the selection and sets
  query = suggestion.title. No map move. No detail view.
  (Product Detail is deferred to Phase 8 — see comment in code.)
  Suggestions are cleared. Dropdown closes.

  ↓  (OR)

Step 6b — User presses Enter instead of clicking a suggestion.
  onKeyDown triggers handleEnterSearch().
  The pending autocomplete request is aborted immediately.
  suggestions are cleared.
  listingQuery = trimmed query.
  listingResults = [].
  listingLoading = true.
  searchView transitions to 'listing'.
  The sidebar Sheet opens (isSidebarOpen becomes true).
  SearchListing renders with loading spinner.

  ↓

Step 7 — Full search request is sent.
  adapter.search(query, locationBias) is called.
  → SearchEngineAdapter.search() delegates to ProductSearchEngine.search().
  → ProductSearchEngine calls ProductSearchService.search(query, signal).
  → ProductSearchService fetches:
      GET /api/products/search?query=m%E1%BA%ADt+ong&limit=20&offset=0
  → Backend: ProductSearchController receives the request.
  → Controller reads query, limit (default 20), offset (default 0).
  → Controller validates query non-empty (returns 400 if missing).
  → Controller calls productSearchService.search(query, limit, offset).
  → Backend ProductSearchService queries Meilisearch index "products":
      attributesToRetrieve: ["id", "name", "short_description"]
      limit, offset
  → Meilisearch runs full-text search with ranking rules, typo tolerance,
    synonyms, and stop words as defined in products.settings.ts.
  → Meilisearch returns matching hits.
  → Backend maps hits to ProductListingItem[]:
      { id, name, short_description, image: null }
  → Backend returns ProductListingResponse inside { success, data } envelope.

  ↓

Step 8 — Response received by frontend.
  productSearch.service.ts extracts envelope.data.items (ProductListingItem[]).
  ProductSearchEngine passes them to SearchSuggestionMapper.fromProducts().
  Mapper converts each item to SearchSuggestion:
      { id: product.id, type: 'product', title: product.name,
        description: product.short_description, image: undefined, original: product }
  SearchBar receives SearchSuggestion[].
  SearchBar.setListingResults(results.slice(0, 20)).
  listingLoading = false.

  ↓

Step 9 — Listing renders inside the sidebar.
  SearchListing receives results[], loading=false, query=listingQuery.
  Header shows count: "N found".
  Subheader shows the query string in quotes.
  Each SearchListingCard renders:
    - 64x64 thumbnail area: if result.image is set → <img />;
      if result.image is undefined → <ImageIcon /> placeholder.
    - Title: result.title (product name), semibold, truncated.
    - Description: result.description (short_description), 2-line clamp.
  Clicking a card fires handleListingSelect(suggestion).
  For product type: logs selection, updates query text. No navigation.
  (Phase 8: will open Product Detail panel.)

  ↓

Step 10 — User types again while listing is visible.
  handleQueryChange detects searchView === 'listing' and switches to 'refining'.
  The listing stays visible behind the new autocomplete dropdown.
  A new autocomplete request fires via the debounce effect.
  When the user presses Enter again, a new listing request replaces the old one.

Purpose:

Responsibility:

------------------------------------------------------------------------
FILE: frontend/src/features/search/types/SearchSuggestion.ts
------------------------------------------------------------------------
Purpose:
  Defines the frozen SearchSuggestion DTO — the ONLY data shape
  that any UI component in the search feature ever touches.

Responsibility:
  Acts as the anti-corruption boundary between search providers and UI.
  Both place results and product results must be converted to this shape
  before entering the presentation layer.

Main Exports:
  interface SearchSuggestion {
    id: string;
    type: 'place' | 'product';
    title: string;
    description: string;
    image?: string;
    location?: { lat: number; lng: number };
    original: unknown;
  }

Field Explanations:
  id          — stable React key; for products = product.id; for places = place.id
  type        — determines icon: 'place' → MapPin, 'product' → ShoppingBag
  title       — primary display text; for products = product.name
  description — secondary display text; for products = short_description
  image       — optional thumbnail URL; null becomes undefined at mapper level
  location    — coordinates; present for places only; absent for products
  original    — raw provider object (PlaceSuggestion or ProductListingItem);
                stored for Phase 8 callbacks that need provider-specific data

Why This File Exists:
  The frozen DTO guarantee means SearchBar, SearchResult, SearchListing, and
  SearchListingCard never need to import or know about Map4D or Meilisearch
  types. Adding a new search provider only requires implementing SearchEngine
  and writing one new mapper method.

------------------------------------------------------------------------
FILE: frontend/src/features/search/services/SearchEngine.ts
------------------------------------------------------------------------
Purpose:
  Defines the SearchEngine interface — the Dependency Inversion boundary.

Responsibility:
  Establishes the contract that every concrete search engine must honour.
  Labelled "ARCHITECTURE FREEZE (Phase 7.4)".

Main Exports:
  interface SearchEngine {
    autocomplete(query, locationBias?, signal?): Promise<SearchSuggestion[]>;
    search(query, locationBias?, signal?): Promise<SearchSuggestion[]>;
  }

Important Notes:
  Both methods always return SearchSuggestion[] — never provider-native types.
  locationBias is passed per-call (not in constructor) so the adapter remains
  stateless and SearchBar does not need to recreate the adapter on map pan.

Communicates With:
  SearchEngineAdapter.ts — holds a private engine: SearchEngine.
  Map4DSearchEngine.ts — implements this interface.
  ProductSearchEngine.ts — implements this interface.

Why This File Exists:
  Without this interface the SearchBar would need to import
  ProductSearchEngine and Map4DSearchEngine directly, coupling UI to
  infrastructure. The interface enables the Open/Closed Principle: new
  engines can be added without modifying SearchBar or SearchEngineAdapter.

------------------------------------------------------------------------
FILE: frontend/src/features/search/services/SearchEngineAdapter.ts
------------------------------------------------------------------------
Purpose:
  Strategy Pattern gateway — the ONLY search class SearchBar imports.

Responsibility:
  1. Accept a SearchMode in the constructor.
  2. Instantiate the correct concrete SearchEngine.
  3. Expose autocomplete() and search() that delegate to the engine.
  4. Forward locationBias per-call (adapter is stateless between calls).

Main Exports:
  class SearchEngineAdapter {
    constructor(mode: SearchMode)
    autocomplete(query, locationBias?, signal?): Promise<SearchSuggestion[]>
    search(query, locationBias?, signal?): Promise<SearchSuggestion[]>
  }

Constructor Logic:
  if (mode === 'place')   → this.engine = new Map4DSearchEngine()
  else                    → this.engine = new ProductSearchEngine()

Communicates With:
  SearchBar.tsx — SearchBar creates the adapter via useMemo([searchMode]).
  ProductSearchEngine.ts — instantiated when mode = 'product'.
  Map4DSearchEngine.ts — instantiated when mode = 'place'.

Why This File Exists:
  If this file did not exist, SearchBar would contain:
    if (mode === 'product') { ProductSearchService.autocomplete(...) }
    else { SearchService.searchPlaces(...) }
  That would couple the top-level UI to infrastructure. The adapter
  prevents that coupling entirely.

------------------------------------------------------------------------
FILE: frontend/src/features/search/services/ProductSearchEngine.ts
------------------------------------------------------------------------
Purpose:
  Concrete SearchEngine implementation for the product search workflow.

Responsibility:
  1. Implement SearchEngine interface.
  2. Call ProductSearchService for HTTP communication.
  3. Pass results through SearchSuggestionMapper.
  4. Silently ignore locationBias (products have no geographic component).

Main Exports:
  class ProductSearchEngine implements SearchEngine {
    async autocomplete(query, _locationBias?, signal?): Promise<SearchSuggestion[]>
    async search(query, _locationBias?, signal?): Promise<SearchSuggestion[]>
  }

autocomplete() flow:
  Guard: if (!query.trim()) return [].
  Calls ProductSearchService.autocomplete(query, signal) → AutocompleteItem[].
  Calls SearchSuggestionMapper.fromAutocompleteItems(items) → SearchSuggestion[].

search() flow:
  Guard: if (!query.trim()) return [].
  Calls ProductSearchService.search(query, signal) → ProductListingItem[].
  Calls SearchSuggestionMapper.fromProducts(items) → SearchSuggestion[].

Communicates With:
  ProductSearchService (frontend) — HTTP communication layer.
  SearchSuggestionMapper — converts DTOs to SearchSuggestion.
  SearchEngine interface — contract it implements.
  SearchEngineAdapter — instantiated by the adapter.

Why This File Exists:
  Keeps the HTTP knowledge (ProductSearchService) and the mapping knowledge
  (SearchSuggestionMapper) out of both SearchEngineAdapter and SearchBar.
  This is the one class that coordinates the two lower-level classes.

------------------------------------------------------------------------
FILE: frontend/src/features/search/services/SearchSuggestionMapper.ts
------------------------------------------------------------------------
Purpose:
  The ONLY place where provider-specific types are converted to
  SearchSuggestion. Labelled "ARCHITECTURE FREEZE (Phase 7.4)".

Responsibility:
  Pure static functions. No React. No state. No side effects. No network.
  One direction only: provider DTO → SearchSuggestion.

Main Exports:
  class SearchSuggestionMapper {
    static fromPlace(place: PlaceSuggestion): SearchSuggestion
    static fromAutocompleteItem(item: AutocompleteItem): SearchSuggestion
    static fromProduct(product: ProductListingItem): SearchSuggestion
    static fromPlaces(places: PlaceSuggestion[]): SearchSuggestion[]
    static fromAutocompleteItems(items: AutocompleteItem[]): SearchSuggestion[]
    static fromProducts(products: ProductListingItem[]): SearchSuggestion[]
  }

Mapping: fromAutocompleteItem(item)
  id          = item.name   (name is unique in dropdown)
  type        = 'product'
  title       = item.name
  description = ''          (autocomplete endpoint has no description)
  original    = item

Mapping: fromProduct(product)
  id          = product.id
  type        = 'product'
  title       = product.name
  description = product.short_description ?? ''
  image       = product.image ?? undefined  (null becomes undefined)
  original    = product

Communicates With:
  ProductSearchEngine.ts — calls fromAutocompleteItems() and fromProducts().
  Map4DSearchEngine.ts — calls fromPlaces().
  SearchSuggestion type — the output shape.

Why This File Exists:
  Centralising the mapping logic means that if a backend DTO field is
  renamed, only this file changes. UI components (SearchResult,
  SearchListing, SearchListingCard) never need updating.

FILE: frontend/src/services/meilisearch/productSearch.service.ts
------------------------------------------------------------------------
Purpose:
  HTTP client for the Product Search backend endpoints.
  Hides all network fetch logic from the engine layer.

Responsibility:
  - Build and execute fetch() calls.
  - Unwrap the { success, data } response envelope.
  - Support AbortSignal for request cancellation.
  - Return typed arrays (AutocompleteItem[] or ProductListingItem[]).

Main Exports:
  interface AutocompleteItem { name: string }
  interface ProductListingItem { id, name, short_description, image }
  interface ProductListingResponse { query, processingTimeMs, estimatedTotalHits, items }
  class ProductSearchService {
    static async autocomplete(query, signal?): Promise<AutocompleteItem[]>
    static async search(query, signal?, limit?, offset?): Promise<ProductListingItem[]>
  }

Environment:
  const API_URL = import.meta.env.VITE_BACKEND_URL

autocomplete() endpoint:
  GET ${API_URL}/api/products/autocomplete?query=${encodeURIComponent(query)}

search() endpoint:
  GET ${API_URL}/api/products/search?query=${encodeURIComponent(query)}&limit=${limit}&offset=${offset}

Error handling:
  If response.ok is false → throws Error.
  If AbortSignal aborts → the fetch rejects with AbortError, propagated up.

Why This File Exists:
  Keeps the HTTP fetch concern separated from the engine and mapper.
  If the backend URL or response envelope ever changes, only this file
  changes — not the engine, not the mapper, not the UI.

  SearchResult — receives suggestions[], onSelectSuggestion.
  SearchListing — receives results[], loading, query, onSelectItem.

Exports:
  export const SearchBar: React.FC<SearchBarProps>
  export default SearchBar

Why This File Exists:
  Centralises all search state so child components remain pure/presentational.
  SearchBar is the single point of truth for what the user has typed and what
  results are available.

================================================================================
5. FRONTEND FLOW
================================================================================

LAYER 1 — SearchBar.tsx
  Owns all search state. Debounces user input (350 ms). Creates
  SearchEngineAdapter via useMemo. Fires autocomplete() on debouncedQuery
  change. Fires search() on Enter key. Renders all child components.

  ↓

LAYER 2 — SearchMode ('product')
  A simple string type: "place" | "product".
  When searchMode = 'product', the adapter creates a ProductSearchEngine.
  When searchMode = 'place', the adapter creates a Map4DSearchEngine.
  Mode switch clears all stale results and resets to idle view.

  ↓

LAYER 3 — SearchEngineAdapter
  Receives searchMode in constructor (via useMemo).
  Exposes: autocomplete(query, locationBias?, signal?)
           search(query, locationBias?, signal?)
  Both methods return Promise<SearchSuggestion[]> regardless of mode.
  This is the ONLY search class SearchBar imports.

  ↓

LAYER 4 — ProductSearchEngine
  Implements SearchEngine interface.
  autocomplete() → calls ProductSearchService.autocomplete() → mapper.
  search()       → calls ProductSearchService.search() → mapper.
  locationBias is accepted but intentionally ignored (products are not geo-tagged).

  ↓

LAYER 5 — ProductSearchService (frontend)
  Static class. No React. No state.
  autocomplete(): GET /api/products/autocomplete?query=...
  search():       GET /api/products/search?query=...&limit=...&offset=...
  Both methods accept AbortSignal for cancellation.
  Returns AutocompleteItem[] or ProductListingItem[].

  ↓

LAYER 6 — SearchSuggestionMapper
  Static class. Pure functions. No side effects.
  fromAutocompleteItems(items) → SearchSuggestion[] (for dropdown)
  fromProducts(products)       → SearchSuggestion[] (for listing)
  This is the ONLY place where provider types become SearchSuggestion.

  ↓

LAYER 7 — SearchSuggestion DTO
  The frozen universal type consumed by all UI layers.
  { id, type:'product', title, description, image?, location:absent, original }

  ↓  (two paths)

LAYER 8A — SearchResult (Dropdown)
  Receives SearchSuggestion[] from suggestions state.
  Renders a Command palette below the input.
  ShoppingBag icon for product suggestions.
  Fires onSelectSuggestion when user selects.

  ↓

LAYER 8B — SearchListing (Full Listing Panel)
  Receives SearchSuggestion[] from listingResults state.
  Renders inside the sidebar Sheet (left side panel).
  Shows loading spinner, empty state, or list of cards.

  ↓

LAYER 9 — SearchListingCard
  Receives one SearchSuggestion.
  Renders 64x64 thumbnail (image or placeholder) + title + description.
  Fires onSelect when clicked.


================================================================================
6. BACKEND FLOW
================================================================================

CONTROLLER LAYER
  GET /api/products/search?query=...&limit=20&offset=0
  → ProductSearchController.search(req, res)

  Validation:
    query = String(req.query.query ?? "").trim()
    if (!query) → 400 { success: false, message: "Query is required." }
    limit  = Number(req.query.limit ?? 20)
    offset = Number(req.query.offset ?? 0)

  Delegates to:
    productSearchService.search(query, limit, offset)

  ↓

  GET /api/products/autocomplete?query=...&limit=5
  → ProductAutocompleteController.autocomplete(req, res)

  Validation:
    query = String(req.query.query ?? "").trim()
    if (!query) → 400 { success: false, message: "Query is required." }
    limit  = Number(req.query.limit ?? 5)

  Delegates to:
    productSearchService.autocomplete(query, limit)

  ↓

SERVICE LAYER (backend/src/meilisearch/services/ProductSearchService.ts)

  search(query, limit, offset):
    const client = await meiliClientPromise
    const result = await client.index('products').search<ProductSearchDocument>(query, {
      limit, offset,
      attributesToRetrieve: ["id", "name", "short_description"]
    })
    Maps hits → ProductListingItem[] (image: null for all)
    Returns ProductListingResponse { query, processingTimeMs, estimatedTotalHits, items }

  autocomplete(query, limit):
    const client = await meiliClientPromise
    const result = await client.index('products').search(query, {
      limit,
      attributesToRetrieve: ["name"]
    })
    Maps hits → AutocompleteItem[] ({ name } only)
    Returns AutocompleteResponse { query, processingTimeMs, estimatedTotalHits, items }

  ↓

MEILISEARCH CLIENT (meiliClientPromise)
  Singleton Meilisearch JS client.
  Loaded once via dynamic import() (CJS→ESM interop).
  Host: MEILISEARCH_HOST env variable.
  Key:  MEILISEARCH_ADMIN_KEY env variable.

  ↓

MEILISEARCH SEARCH ENGINE
  Runs full-text search on the "products" index.
  Applies: ranking rules, typo tolerance, synonyms, stop words, dictionary.

  ↓

SEARCH INDEX ("products")
  Contains ProductSearchDocument records.
  Primary key: "id".
  Searchable: name, name_en, danh_muc, short_description.
  Filterable: danh_muc.

  ↓

RAW HITS (ProductSearchDocument[])
  Mapped to clean DTOs by ProductSearchService before leaving the method.

  ↓

RESPONSE DTO
  ProductListingResponse or AutocompleteResponse.

  ↓

HTTP RESPONSE
  Controller wraps in: { success: true, data: result }
  Status: 200 OK.
  On error: { success: false, message: "..." } with status 500.

9. MAPPERS
================================================================================

FRONTEND MAPPER — SearchSuggestionMapper
-----------------------------------------

Purpose:
  The ONLY place where provider-specific types are converted to SearchSuggestion.
  All three methods are pure functions with no side effects.

Method 1: fromAutocompleteItem(item: AutocompleteItem) → SearchSuggestion
  Input  : AutocompleteItem { name: string }
  Output : SearchSuggestion {
             id: item.name,         (name doubles as stable key in dropdown)
             type: 'product',
             title: item.name,
             description: '',       (autocomplete has no description)
             original: item
           }
  Why empty description: The autocomplete endpoint returns only { name }
  for performance. No category, no short_description is fetched.

Method 2: fromProduct(product: ProductListingItem) → SearchSuggestion
  Input  : ProductListingItem { id, name, short_description, image }
  Output : SearchSuggestion {
             id: product.id,
             type: 'product',
             title: product.name,
             description: product.short_description ?? '',
             image: product.image ?? undefined,   (null → undefined)
             original: product
           }
  Why image null→undefined: SearchListingCard checks if (result.image)
  truthy to decide between <img> and placeholder. null is falsy but the
  type says "string | undefined", so the mapper coerces null to undefined
  for a clean type contract.

Method 3: fromPlace(place: PlaceSuggestion) → SearchSuggestion
  Used by Map4DSearchEngine. Not part of Product Search but lives in the
  same mapper class for cohesion.

Batch helpers:
  fromPlaces()            → places.map(fromPlace)
  fromAutocompleteItems() → items.map(fromAutocompleteItem)
  fromProducts()          → products.map(fromProduct)

BACKEND MAPPER — ProductTypeMapper
------------------------------------

Purpose:
  Transforms a raw Supabase product_types row into a ProductSearchDocument
  suitable for Meilisearch indexing.

Method: toSearchDocument(product: any) → ProductSearchDocument
  Input  : raw Supabase row (untyped — schema varies)
  Output : ProductSearchDocument (typed, normalised)
  - slug: trim + lowercase
  - string fields: coalesced to '' if null
  - array fields (cong_dung, huong_dan_su_dung): ensured arrays

Used Only During Indexing:
  This mapper runs at sync time (sync-product-types.ts script).
  It does NOT run during live search requests.

WHY MAPPERS EXIST
------------------
1. Anti-corruption: Backend Meilisearch documents and frontend HTTP DTOs
   are internal shapes. If they change, only the mapper changes.
2. Decoupling: UI components (SearchResult, SearchListing, SearchListingCard)
   never import AutocompleteItem or ProductListingItem. They only import
   SearchSuggestion. This means the entire backend can be changed or replaced
   without touching a single UI component.
3. Single responsibility: Mapping logic is not scattered across engines,
   services, or UI components. It is in exactly one place per direction.
4. Testability: Pure functions are trivially unit-testable with zero mocking.

10. SEARCH ENGINE
================================================================================

SearchEngine INTERFACE (frontend/src/features/search/services/SearchEngine.ts)
  The Dependency Inversion boundary. Marked "ARCHITECTURE FREEZE (Phase 7.4)".
  All consumers depend on this interface — never on a concrete class.

  interface SearchEngine {
    autocomplete(query, locationBias?, signal?): Promise<SearchSuggestion[]>;
    search(query, locationBias?, signal?): Promise<SearchSuggestion[]>;
  }

  Rules:
  - Both methods return SearchSuggestion[] — always. Never provider types.
  - locationBias is per-call (stateless adapter).
  - AbortSignal is optional for cancellation.
  - The interface is permanently frozen. Future engines implement it.

ProductSearchEngine (frontend/src/features/search/services/ProductSearchEngine.ts)
  Concrete implementation for product mode.
  Ignores locationBias (_locationBias) — products have no geo-component.
  autocomplete() → ProductSearchService.autocomplete() → mapper.fromAutocompleteItems()
  search()       → ProductSearchService.search()       → mapper.fromProducts()

SearchEngineAdapter (frontend/src/features/search/services/SearchEngineAdapter.ts)
  Strategy Pattern. Holds private engine: SearchEngine.
  Constructor selects concrete engine based on SearchMode:
    'place'   → new Map4DSearchEngine()
    'product' → new ProductSearchEngine()
  autocomplete() and search() simply delegate to this.engine.

DEPENDENCY INVERSION PRINCIPLE
  High-level module: SearchBar
  Depends on: SearchEngineAdapter (which depends on SearchEngine interface)
  Low-level modules: Map4DSearchEngine, ProductSearchEngine
  SearchBar never imports any concrete engine or service.

OPEN/CLOSED PRINCIPLE
  Adding a third search mode (e.g. 'event') requires:
  1. Add 'event' to SearchMode type.
  2. Create EventSearchEngine implements SearchEngine.
  3. Add one new branch in SearchEngineAdapter constructor.
  SearchBar.tsx changes ZERO lines.

WHY SEARCHBAR KNOWS NOTHING ABOUT ProductSearchService
  SearchBar imports only:
    SearchEngineAdapter — the adapter
    SearchSuggestion — the frozen DTO
    SearchMode — the mode type
  SearchBar does NOT import:
    ProductSearchService, ProductSearchEngine, Map4DSearchEngine,
    SearchSuggestionMapper, AutocompleteItem, ProductListingItem,
    PlaceSuggestion, SearchService.

  This means SearchBar can be moved, reused, or replaced without
  dragging any search-provider dependencies with it.

11. DROPDOWN
================================================================================

HOW THE DROPDOWN WORKS
  The autocomplete dropdown (SearchResult) appears when:
  1. suggestions.length > 0 (at least one item from adapter.autocomplete())
  2. searchView is 'autocomplete' or 'refining'

  The dropdown is rendered directly in SearchBar.tsx below the input:
    {suggestions.length > 0 && (
      <SearchResult suggestions={suggestions} onSelectSuggestion={handleSuggestionSelect} />
    )}

  It is positioned absolutely relative to the search input container:
    className="absolute top-full left-0 right-0 mt-2 z-50"

FILES THAT RENDER THE DROPDOWN
  SearchBar.tsx — controls visibility (suggestions.length > 0).
  SearchResult.tsx — renders the Command palette UI.

FILES THAT PROVIDE DATA
  SearchEngineAdapter.ts → ProductSearchEngine.ts →
  ProductSearchService.ts → backend /api/products/autocomplete →
  ProductSearchService (backend) → Meilisearch.

HOW AUTOCOMPLETE REQUESTS ARE MADE
  1. User types → query state updates via handleQueryChange.
  2. useDebounce(query, 350) waits 350 ms after the last keystroke.
  3. The autocomplete useEffect fires on debouncedQuery change.
  4. An AbortController is created for this request.
  5. adapter.autocomplete(debouncedQuery, locationBias, abortController.signal) is called.
  6. Results arrive → setSuggestions(results).
  7. SearchResult renders the dropdown.

HOW AbortController WORKS
  Every time the autocomplete useEffect fires, a new AbortController is created:
    const abortController = new AbortController();
    autocompleteAbortRef.current = abortController;

  The previous request is cancelled by the useEffect cleanup function:
    return () => {
      abortController.abort();
      autocompleteAbortRef.current = null;
    };

  When debouncedQuery changes (the user types more), React:
  1. Runs the cleanup of the previous effect run → aborts the old request.
  2. Runs the new effect → creates a new AbortController → makes a new request.

  This means only the LATEST in-flight autocomplete request is ever live.
  If the user types "m", then "ma", then "mật", three requests are fired
  but only the last one ("mật") is allowed to complete. The previous two
  are aborted via AbortSignal, causing their fetch() to reject with AbortError.

HOW OLD REQUESTS ARE CANCELLED
  In ProductSearchService.autocomplete():
    const response = await fetch(url, { signal });
  
  When the AbortController fires signal.abort(), the fetch rejects with
  an AbortError (DOMException with name 'AbortError').

  In SearchBar's autocomplete effect catch handler:
    .catch((err: unknown) => {
      if (err instanceof Error && err.name !== 'AbortError') {
        setSuggestions([]);
        showToast('Failed to fetch autocomplete suggestions.');
      }
    });
  
  AbortErrors are silently ignored. Only genuine network/server errors
  show the toast.

  Additionally, when the user presses Enter (handleEnterSearch):
    autocompleteAbortRef.current?.abort();
    autocompleteAbortRef.current = null;
  
  This aborts any pending autocomplete request immediately before the
  full search request begins.

12. LISTING
================================================================================

HOW LISTING WORKS
  After the user presses Enter, handleEnterSearch() fires:
  1. Pending autocomplete request is aborted.
  2. setSuggestions([]) — clears dropdown.
  3. setListingQuery(trimmed) — stores the query for display.
  4. setListingResults([]) — clears old results.
  5. setListingLoading(true) — activates spinner.
  6. setSearchView('listing') — opens the sidebar Sheet.
  7. await adapter.search(trimmed, locationBias) — calls backend.
  8. setListingResults(results.slice(0, 20)) — stores results (cap at 20).
  9. setListingLoading(false) — removes spinner.

WHICH COMPONENT RENDERS IT
  SearchListing.tsx — receives results[], loading, query, onSelectItem.
  SearchListingCard.tsx — renders each individual card.
  Both are mounted inside the Sheet (sidebar) in SearchBar.tsx:
    {(searchView === 'listing' || searchView === 'refining') && (
      <SearchListing results={listingResults} loading={listingLoading}
        query={listingQuery} onSelectItem={handleListingSelect} />
    )}

WHICH DTO IT RECEIVES
  SearchListing receives SearchSuggestion[] (the frozen DTO).
  It never receives ProductListingItem[] directly.

WHICH MAPPER PROVIDES DATA
  SearchSuggestionMapper.fromProducts(items) converts ProductListingItem[]
  → SearchSuggestion[] inside ProductSearchEngine.search(). By the time
  SearchListing receives the array, all products are already SearchSuggestion.

HOW SearchListingCard RENDERS PRODUCT ITEMS

  Image / Thumbnail Area:
    if (result.image) → <img src={result.image} alt={result.title} className="w-full h-full object-cover" />
    else              → <ImageIcon className="h-6 w-6 text-muted-foreground/40" />
  
  IMAGE PLACEHOLDER:
    Currently, all products have image: null in the Meilisearch index.
    The backend ProductSearchService.search() hardcodes image: null.
    The frontend mapper converts null → undefined (falsy check passes).
    Therefore ALL product cards currently render the <ImageIcon /> placeholder.
    When product images are added to the Meilisearch index, only
    ProductSearchService.search() needs one line change. No UI changes needed.

  TITLE:
    <p className="text-sm font-semibold leading-snug text-foreground truncate">
      {result.title}
    </p>
    result.title = product.name (e.g. "Mật ong rừng Sơn Trà")
    Single line, truncated with ellipsis.

  DESCRIPTION:
    {result.description && (
      <p className="text-justify text-xs text-muted-foreground leading-snug line-clamp-2 ...">
        <span>{result.description}</span>
      </p>
    )}
    result.description = product.short_description
    Shown only if non-empty. Clamped to 2 lines.
    For autocomplete suggestions: description is '' → not shown.
    For full search results: description is short_description → shown.

  ON SELECT:
    <button onClick={() => onSelect(result)}> ... </button>
    → calls handleListingSelect(suggestion) in SearchBar.
    → for product type: logs selection, sets query = title.
      No map move. No navigation. (Phase 8: Product Detail.)

13. CURRENT LIMITATIONS
================================================================================

1. NO PRODUCT DETAIL PAGE
   Selecting a product from the dropdown or listing only logs the selection
   and updates the query input text. There is no product detail panel, no
   product page, no route navigation. This is explicitly deferred to Phase 8.
   Code comment: "Phase 7.5.5 — Product Detail is built in Phase 8."

2. IMAGE PLACEHOLDER ONLY
   All product cards display the <ImageIcon /> placeholder because image is
   always null in the Meilisearch index. No product image URLs have been
   indexed yet. The DTO slot (image: string | null) is reserved.

3. NO PRODUCT NAVIGATION
   Clicking a product does not navigate to any URL. There is no product
   detail route registered in the frontend router.

4. NO BOOKMARK / FAVORITE
   No mechanism to save, bookmark, or favorite a product exists.

5. NO PAGINATION
   The frontend caps results at 20 (results.slice(0, 20)).
   There is no "load more" button, no infinite scroll, no page numbers.
   The backend supports offset parameter but the frontend does not use it.

6. NO CATEGORY FILTERING
   danh_muc is a filterable attribute in Meilisearch settings but no UI
   filter controls exist. All results are returned regardless of category.

7. NO SORTING
   No sort controls exist in the UI. Results are sorted only by Meilisearch's
   internal ranking rules.

8. NO GEOLOCATION COMPONENT
   Product search ignores locationBias entirely. Products are not geo-tagged.

9. NO PRODUCT LISTING PAGE (STANDALONE)
   Product search results only appear inside the sidebar Sheet, attached to
   the map interface. There is no dedicated /products route.

10. getById NOT IMPLEMENTED
    backend/src/meilisearch/services/ProductSearchService.getById(id) throws:
    "getById(id) — Not implemented (Phase 8)."

11. useProductSearch HOOK NOT USED IN MAIN FLOW
    The useProductSearch hook exists but is not used by SearchBar or any
    active component in the current search flow. SearchBar uses the adapter
    pattern instead.

12. SEARCH RESULT LIMIT IS HARDCODED
    SearchBar caps listing results to 20 (results.slice(0, 20)) regardless
    of what the backend returns.

13. NO EMPTY AUTOCOMPLETE GUARD ON ENGINE LEVEL
    ProductSearchEngine guards empty queries but SearchBar also has its own
    guard (debouncedQuery.trim().length < 1). There is mild redundancy.

17. DEBUGGING GUIDE
================================================================================

ISSUE: Dropdown is empty after typing
  Step 1 — Check browser DevTools Network tab.
    Is GET /api/products/autocomplete?query=... being sent?
    If NOT: check that searchMode is 'product' (not 'place').
    If NOT: check that debouncedQuery.trim().length >= 1 (debounce delay?).
  Step 2 — Is the request being aborted?
    In DevTools, look for "cancelled" status. Normal — means a newer request
    replaced it. If ALL requests are cancelled, check AbortController logic.
  Step 3 — Is the backend responding?
    Check response status. 400 = query param missing. 500 = Meilisearch error.
  Step 4 — Is the Meilisearch index empty?
    Run the sync script: npx ts-node backend/src/meilisearch/scripts/sync-product-types.ts
  Step 5 — Is MEILISEARCH_HOST correct in backend .env?
    Check backend/.env: MEILISEARCH_HOST=http://localhost:7700
  Step 6 — Is the frontend VITE_BACKEND_URL set?
    Check frontend/.env: VITE_BACKEND_URL=http://localhost:5000
  Step 7 — Is the backend running?
    Check that the Express server is listening on port 5000.

ISSUE: Listing is empty after pressing Enter
  Step 1 — Check Network tab for GET /api/products/search?query=...
  Step 2 — Check response. 400 = query missing. 500 = Meilisearch error.
  Step 3 — Is estimatedTotalHits 0?
    The query returned no matches. Try a simpler query ("cafe", "mật").
    Check Meilisearch index has documents (use Meilisearch dashboard).
  Step 4 — Are results being sliced to 0?
    Check that results.slice(0, 20) is not slicing an empty array.
    Add console.log(results) in SearchBar.handleEnterSearch() after adapter.search().
  Step 5 — Is listingResults state being set?
    Add console.log in setListingResults callback.

ISSUE: API error (HTTP 500)
  Step 1 — Check backend console for error log:
    "[ProductSearchController] search error:" or console.error(error)
  Step 2 — Meilisearch not running?
    GET http://localhost:7700/health → should return { "status": "available" }
  Step 3 — Wrong MEILISEARCH_ADMIN_KEY?
    Meilisearch returns 401 or 403. Check backend .env.
  Step 4 — Index "products" does not exist?
    GET http://localhost:7700/indexes/products with the admin key.
    If 404: run the sync script to create and populate the index.

ISSUE: Network error (fetch fails entirely)
  Step 1 — Is the backend server running?
    curl http://localhost:5000/health → should return { "status": "OK" }
  Step 2 — CORS error in browser?
    Check browser console for "CORS policy" error.
    The backend uses app.use(cors()) globally — ensure it is active.
  Step 3 — Wrong VITE_BACKEND_URL?
    Check frontend/.env for VITE_BACKEND_URL.
    After .env changes, restart Vite dev server (npm run dev).

ISSUE: Mapper error (unexpected data shape)
  Step 1 — Log the raw response in ProductSearchService:
    console.log(envelope) inside productSearch.service.ts.
  Step 2 — Check that envelope.data.items is an array.
    If undefined: backend returned unexpected shape.
  Step 3 — Check ProductListingItem fields:
    If id is missing: check backend AttributesToRetrieve list.
    If name is missing: check Meilisearch document has name field.
  Step 4 — Check SearchSuggestionMapper.fromProduct():
    Add console.log(product) before the return statement.

ISSUE: Adapter error (wrong engine selected)
  Step 1 — Log searchMode in SearchBar:
    console.log('[SearchBar] searchMode:', searchMode)
  Step 2 — Verify SearchEngineAdapter constructor branch:
    console.log('[SearchEngineAdapter] mode:', mode)
  Step 3 — Verify which engine method is called:
    Add console.log to ProductSearchEngine.autocomplete() entry.

ISSUE: Wrong data (product results appear in place mode)
  This should be impossible by design. Verify that:
  - SearchEngineAdapter constructor uses the correct branch.
  - The adapter is recreated when mode changes (useMemo([searchMode])).
  - No stale closure is holding the old adapter.

ISSUE: No response (fetch hangs)
  Step 1 — Check if AbortController aborted early.
  Step 2 — Set a timeout: is Meilisearch responding slowly?
    GET http://localhost:7700/health — if slow, Meilisearch is overloaded.
  Step 3 — Check network tab: is the request pending?
    If pending indefinitely → backend is not sending a response.
    Add try/catch logging in the controller.

ISSUE: Toast "Failed to fetch autocomplete suggestions" appears
  This fires for errors that are NOT AbortError.
  Step 1 — Check Network tab for the autocomplete request status.
  Step 2 — If 500: backend error → check backend logs.
  Step 3 — If net::ERR_CONNECTION_REFUSED: backend not running.
  Step 4 — If net::ERR_NETWORK_CHANGED: transient network issue.

18. SUMMARY
================================================================================

HOW PRODUCT SEARCH WORKS
  The user clicks "Product Search" in the mode switcher. From that moment,
  every keystroke debounce triggers a GET /api/products/autocomplete request
  to the backend, which queries Meilisearch and returns up to 5 product names.
  These are mapped to SearchSuggestion DTOs and rendered in the dropdown.
  When the user presses Enter, a GET /api/products/search request fetches up
  to 20 full ProductListingItem results. These are mapped to SearchSuggestion
  and rendered as cards in the sidebar listing panel.

WHY THE ARCHITECTURE IS CLEAN
  Every layer has exactly one responsibility:
  - SearchBar: state management and orchestration
  - SearchEngineAdapter: strategy selection
  - ProductSearchEngine: engine-level coordination
  - ProductSearchService (frontend): HTTP communication
  - SearchSuggestionMapper: type conversion
  - SearchSuggestion: the universal DTO
  - Backend controllers: HTTP validation
  - Backend ProductSearchService: Meilisearch communication and anti-corruption
  - Meilisearch: full-text search

HOW EVERY LAYER IS SEPARATED
  The frontend presentation layer (SearchResult, SearchListing, SearchListingCard)
  depends ONLY on SearchSuggestion. It has zero knowledge of Map4D, Meilisearch,
  AutocompleteItem, or ProductListingItem.

  The engine layer (ProductSearchEngine, Map4DSearchEngine) depends on the
  SearchEngine interface — not on each other or on the presentation layer.

  The adapter layer (SearchEngineAdapter) knows the SearchMode and the
  SearchEngine interface — but nothing about Meilisearch or Map4D internals.

  The service layer (ProductSearchService frontend) knows the HTTP endpoints
  and response envelopes — nothing about React state or UI rendering.

  The mapper (SearchSuggestionMapper) knows provider types and the frozen DTO
  — nothing about HTTP, React, or state.

WHY FUTURE PRODUCT DETAIL CAN BE ADDED WITHOUT MODIFYING SEARCHBAR
  SearchBar already stores the raw provider object in suggestion.original
  (typed as unknown). When Product Detail (Phase 8) is implemented:

  1. A ProductDetailCard component will be created (does not touch SearchBar internals).
  2. handleSuggestionSelect() and handleListingSelect() will cast suggestion.original
     as ProductListingItem to access the full product data.
  3. A new 'product-detail' view state will be added to SearchView.
  4. ProductSearchService.getById(id) will be implemented on the backend.

  SearchBar.tsx will only need the addition of a new case in two handler
  functions and one new rendering block in the JSX — equivalent changes to
  adding the existing POI detail flow. The entire search pipeline, adapter,
  engine, service, and mapper remain untouched.
